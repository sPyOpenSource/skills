Skill Configuration & Agent Integration

Skill System Architecture — Lesson 2 of ?

Lesson 1 covered what a skill is — a SKILL.md file with frontmatter and instructions. But how does the AI agent know which skills exist? How does it decide when to load one? And how does configuration control the behavior?

A skill on disk is just a markdown file. A skill in the agent's hands is the result of a configuration pipeline: discovery → listing → loading → invocation.

Let's look at each step.

2. Step 1: Discovery — opencode.json

Skills are configured in the project's opencode.json (or opencode.jsonc). This is the same file that configures the AI agent for your project. The relevant configuration points:

📁 Skills Directory

"skills": ["path/to/skills"]

Tells opencode where to look for SKILL.md files. Can be a directory or an array of directories.

🔌 Skill Permission

"permissions": {"skill": true}

Whether the agent is allowed to load and run skills. Can be true, false, or a path allowlist.

Note: opencode.json is per-project. Skills directories are typically relative to the project root, e.g., .opencode/skills/ or just skills/. You can have multiple skills directories.

3. Step 2: Listing — available_skills

At the start of a session, opencode reads all SKILL.md files from the configured directories and builds a list. This list is injected into the agent's system prompt as available_skills — a structured list of:

  • name — the skill identifier (from frontmatter)
  • description — what the skill does (from frontmatter)
  • location — path to the SKILL.md file

This is what you see at the start of every session — the full catalog of what the agent could do. Here's a real entry from this repo:

"description": "Diagnosis loop for hard bugs and performance regressions...",
"location": "/Users/xuyi/.config/opencode/skills/.../diagnosing-bugs/SKILL.md",
"name": "diagnosing-bugs"

How the agent uses this list

The system prompt tells the agent:

  1. Scan available_skills at the start of every task
  2. If a skill's description matches what the user is asking for, load it before responding
  3. The agent matches by reading the description field — so descriptions are the key discovery mechanism

Quiz: A user asks "help me diagnose why my app is slow." Which field in available_skills tells the agent which skill to load?

4. Step 3: Loading — the skill Tool

When the agent decides a skill is relevant, it uses the skill tool to load it: 

{
  "name": "skill",
  "description": "Load a specialized skill...",
  "parameters": {
    "name": {"type": "string"}
  }
}

The agent calls skill("diagnosing-bugs") and the tool returns the full SKILL.md content — both frontmatter and body. The instructions are now in the agent's context and the agent follows them.

Key insight: The skill tool loads exactly one skill at a time. The agent chooses which to load based on the descriptions in available_skills. If multiple skills match, the agent should pick the best one (or ask the user).

5. Step 4: Invocation

Once loaded, the skill's body becomes an instruction set. Skills can specify:

  • Trigger phrases — "When the user types /graphify, load this skill before doing anything else"
  • Workflows — step-by-step procedures the agent should follow
  • Tool configurations — which tools to use and how
  • Output formats — how to structure the result

The agent executes the skill's instructions just like any other directive in its system prompt.

6. Putting It All Together: A Real Flow

When you asked me "how skills work," here's what happened under the hood:

  1. System prompt contained available_skills — including writing-skills, customize-opencode, etc.
  2. I scanned descriptions and found the writing-skills skill: "Use when creating new skills, editing existing skills, or verifying skills work before deployment"
  3. The description didn't match well (you wanted to learn about skills, not write one), so I asked you for clarification
  4. You confirmed you wanted to learn the system architecture, so I created this teaching workspace instead of loading a skill
This is a real example of how skill discovery works in practice. The agent read available_skills, evaluated the description fields against your intent, and made a decision. Sometimes the right choice is not to load a skill.

7. The Permission Model

Skills are powerful — they can give the agent custom instructions that modify its behavior. opencode controls this with a permission system:

Permission Value Behavior
"skill": false Agent can't load any skills. available_skills is empty.
"skill": true Agent can load any skill from configured directories.
"skill": ["path/to/skill/SKILL.md"] Only specific skills can be loaded (allowlist).

The permission check happens at load time — when the agent calls the skill tool. If the skill is not permitted, the tool returns an error and the instructions never enter the agent's context.

Summary

  • A skill on disk becomes available to the agent through a four-step pipeline: discovery (opencode.json) → listing (available_skills in system prompt) → loading (skill tool) → invocation (agent follows instructions)
  • The description field in available_skills is how the agent decides which skill to load — it's the most important part of a skill's frontmatter
  • Permissions control whether skills can be loaded at all — set "skill": true in opencode.json
  • Skills are single files loaded on demand — not plugins or modules. The agent reads the markdown and follows the instructions.
  • You saw this pipeline in action at the start of this session: I scanned available_skills, evaluated descriptions against your intent, and decided not to load a skill because none matched well enough
