The Skill Contract

Skills Architecture — from a file on disk to agent behavior

You already know that a skill is a SKILL.md file and that OpenCode can list and load skills. The useful next question is: which part of the skill is doing the work at each moment?

A skill is a contract across layers: the file must be discoverable, its description must make it selectable, its body must make the behavior repeatable, and its permission must allow access.

One Request, Five Boundaries

Trace the request “use OpenCode to implement a feature in an isolated worktree” through the system:

request
  → discovery finds SKILL.md files
  → available_skills lists names and descriptions
  → the agent selects a plausible skill
  → the skill tool loads the full file
  → the agent follows the body and uses referenced tools
Boundary What matters Failure to inspect
Discovery File location and SKILL.md spelling “The skill exists” when it is outside the search paths
Listing name and description A vague description that cannot support selection
Selection Request-to-description fit Expecting the model to infer undocumented intent
Loading The native skill tool and permission A hidden or denied skill being treated as a bad match
Execution The body, references, tools, and completion checks Reading metadata and assuming it is the procedure

Three Parts, Three Jobs

1. The description routes

The description is the small piece of text that helps the agent decide when the skill is relevant. It is not a substitute for the instructions. In this repository, the opencode skill advertises itself as “Delegate coding to OpenCode CLI (features, PR review).” That is routing text: it names the situation, not every command in the body.

2. The body instructs

After selection, the full SKILL.md enters the agent's working context. The body contains the procedure, constraints, examples, and verification. In the same skill, the When to Use, Procedure, and Verification sections do the behavioral work.

3. Companion files extend

References, scripts, templates, and examples can keep the main file focused. They are not automatically a second skill: the agent must be directed to them, and the main file must still contain enough context to use them safely.

Retrieval check: a skill is listed but the agent keeps choosing another skill for a request that clearly needs it. What should you inspect first?

Runtime Contract vs. Repository Convention

The official OpenCode documentation defines the runtime contract: name and description are required, name must match the containing directory, and the description must be specific enough for the agent to choose correctly. OpenCode also documents optional license, compatibility, and metadata fields.

This repository adds conventions such as version, author, platforms, and nested Hermes metadata. Those fields may help this repository's own tooling and human readers. Do not mistake a convention for an OpenCode routing guarantee.

Question Best source
Where does OpenCode search? Official skill documentation and the active project configuration
When should this skill load? The skill's description, interpreted against the user's request
How should the agent proceed? The skill body and any files it explicitly references
Is loading allowed? The agent/tool permission configuration

Summary

  • Discovery finds candidate files; it does not prove they will be selected.
  • Description routes by making a request-to-skill match plausible.
  • Body instructs by supplying the repeatable procedure.
  • Permissions gate loading; they are separate from relevance.
  • Repository conventions and OpenCode's runtime contract are related but not identical.
