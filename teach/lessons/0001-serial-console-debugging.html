Serial Console Debugging

Baremetal Hardware Debugging — Lesson 1 of ?

Your RTOS prints beautifully to the PL011 UART in QEMU. On real hardware, that serial output is your only window into what the CPU is doing — until you get JTAG working. This lesson covers the practical setup and use of the serial console on the BeagleBone AI.

The serial console is the first thing you make work on baremetal. Everything else — exception handlers, timer ticks, model loading — you verify through that one pipe.

What You'll Learn

  • What hardware you need to connect to the BBAI's serial port
  • How your existing UART code maps to the BBAI's UART3 peripheral
  • How to connect, configure the terminal, and verify output
  • A systematic checklist for when you see nothing
  • How to extend your exception handlers to dump useful debug info

1. The Hardware Setup

To see serial output from the BBAI, you need:

  • BBAI board — powered via the 5V barrel jack or micro-USB (USB0)
  • USB-to-UART cable — 3.3V FTDI cable (e.g. FT232RL). Common pinout: black=GND, green=TX, white=RX
  • Dupont wires (female-to-female) to connect the cable to the BBAI's expansion header

The BBAI exposes UART0 on the P9 expansion header:

P9 header (look at the board with the USB ports facing you): P9.24 (pin 11) → UART0 TX → connect to USB-UART RX (white) P9.26 (pin 13) → UART0 RX → connect to USB-UART TX (green) P9.1 (pin 1) → GND → connect to USB-UART GND (black)

Pin numbers on the BBAI P9 header start at 1 (top-left, silk-screened). P9.24 = pin 11, P9.26 = pin 13, P9.1 = pin 1. Double-check with the BBAI System Reference Manual if unsure.

2. Your Code's UART Setup

Your project already has dual-path UART code in src/serial.c:

#ifdef QEMU
#define UART_BASE 0x09000000      // PL011 on QEMU virt
#else
#define UART3_BASE 0x49020000     // UART3 on BBAI
                                     // (connected to expansion header)
#endif
Target UART Base Address Type
QEMU virt PL011 0x09000000 PrimeCell UART
BBAI UART3 0x49020000 TI UART (16750-compat)

Key difference: PL011 and TI UART have different register layouts. Your code handles this with #ifdef QEMU — the BBAI path uses TI UART register offsets (LSR at +0x14, THR/RBR at +0x00).

The BBAI's UART3 is muxed onto the expansion header pins. UART0 is what U-Boot uses by default, but your kernel uses UART3. You connect to UART0 for the U-Boot console; your kernel's output comes from UART3. If you want both on one cable, you can reconfigure U-Boot or change your kernel to use UART0 — but for now, treat them separately.

3. Connecting and Seeing Output

Step 1: Identify the USB-UART device

$ ls /dev/tty.usbserial*
/dev/tty.usbserial-AB0XXXXX

On macOS it's /dev/tty.usbserial-.... On Linux it's /dev/ttyUSB0. On Windows it's COM3 or similar.

Step 2: Connect with screen (or picocom)

$ screen /dev/tty.usbserial-AB0XXXXX 115200

Configure the terminal for 115200 baud, 8 data bits, no parity, 1 stop bit (115200 8N1). This is the BBAI's default UART speed.

Step 3: Power on the BBAI

With the terminal open, apply power. You should see U-Boot boot output immediately. When your kernel runs (chainloaded via U-Boot), its debug output appears on UART3 — connect a second USB-UART to the UART3 pins (see BBAI manual for pinmux assignments) or reconfigure your kernel to use UART0.

4. The "I See Nothing" Checklist

When the terminal stays black, work through this in order:

  1. Is the board powered? — The PWR LED (near the USB port) should be solid. If not, check the power supply (5V, 2A minimum).
  2. Are TX and RX crossed? — The cable's TX goes to the board's RX, and the cable's RX goes to the board's TX. This is the #1 mistake. Swap them and try again.
  3. Is GND connected? — Without a common ground, the signal has no reference. Double-check the black wire.
  4. Is the baud rate correct? — U-Boot defaults to 115200. If you set your screen to 9600 or 57600, you'll see garbage or nothing. Try all common rates (9600, 19200, 38400, 57600, 115200).
  5. Is the cable 3.3V? — 5V cables can damage the BBAI's UART pins. Most FTDI cables are 3.3V or have a jumper; verify yours.
  6. Is UART clocked? — On baremetal, the UART peripheral needs a clock from the PRCM. Check CM_L4PER_UART3_CLKCTRL (at 0x4A009B28). If the module is in DISABLE mode, writes to TX are silently dropped. This is your most likely baremetal pitfall.
  7. Is the pinmux configured? — The UART3 pins need to be muxed to Mode 1 (UART mode). Check the control module padconf registers. Your code handles this in pinmux_init_mmc2() but you may need a pinmux_init_uart3() as well.

5. Making Your Exception Handlers More Useful

Your current exception handlers in src/exception.c already print frame info, but on real hardware you'll want more context. Add these to your data abort handler:

// Inside arch_data_abort_handler, after reading FAR:
unsigned int dfsr;
asm volatile("mrc p15, 0, %0, c5, c0, 0" : "=r" (dfsr));  // Data Fault Status

dprintf("DFSR = %08x\n", dfsr);
dprintf("FAR  = %08x\n", far);

// Decode the status bits
unsigned int status = dfsr & 0x3F;
switch (status) {
    case 0b000001: dprintf("  Cause: Alignment fault\n"); break;
    case 0b000011: dprintf("  Cause: Access flag fault (section)\n"); break;
    case 0b001000: dprintf("  Cause: Precise external abort (parity/ECC)\n"); break;
    case 0b001111: dprintf("  Cause: Domain fault (section)\n"); break;
    case 0b010001: dprintf("  Cause: Translation fault (page)\n"); break;
    default:       dprintf("  Cause: Status code %u\n", status); break;
}

These fault status codes are defined in the ARMv7-A ARM (section B3.11). They are the difference between "something crashed" and "I know exactly why it crashed."

Summary

  • The serial console is your primary debug window on real hardware
  • Your code supports both QEMU PL011 and BBAI UART3 via #ifdef QEMU
  • Connect USB-UART: P9.24 (TX), P9.26 (RX), P9.1 (GND) — 115200 8N1
  • When you see nothing: check power → swap TX/RX → check GND → check baud → check voltage → check PRCM clock → check pinmux
  • Enrich your exception handlers with DFSR/IFSR decoding for faster root cause analysis
